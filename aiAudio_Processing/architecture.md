Act as a pragmatic software architect and hackathon technical lead. Design an implementable architecture and step-by-step execution plan for our three-person hackathon project: **Live Sound Radar**.

## Project and team context

We are building an accessible, non-chat application that listens for environmental sounds, classifies them locally, displays live detections, and produces actionable alerts.

Example sounds include knocking, alarms, and other recognizable environmental events. Choose a small set that the selected model can reliably detect and that we can demonstrate.

We have **one microphone**. “Radar” describes the live awareness interface; do not assume we can determine sound direction, distance, or physical location.

Our baseline pipeline is:

**Microphone → C++ audio capture/processing → local Python sound classifier → live web dashboard and alerts.**

We have three members:

1. **Member 1 — C++/systems:** Strongest in C++, also knows Python. Should own a meaningful C++ audio-processing component.
2. **Member 2 — Python/backend/AI:** Owns local inference and backend integration.
3. **Member 3 — frontend/product:** Owns the dashboard and user interaction.

These are starting responsibilities. Balance the actual workload, especially sponsor integrations, rather than assigning nearly everything to Member 2. We will use agentic coding tools, but need clear architecture, contracts, and acceptance criteria to guide them.

### 4. Exact interface contracts—the edges of the program

This is the most important section. Define contracts concretely enough that members can implement against mocks without waiting for one another.

For every connection, specify:

- Producer and consumer.
- Transport and address/endpoint or function interface.
- Request/response or message schema with a realistic example.
- Required and optional fields, types, units, and allowed values.
- IDs, timestamp format, schema version, and ordering assumptions.
- Success, validation errors, dependency failures, and timeouts.
- Retry behavior, duplicate handling, buffering limits, and backpressure.
- Which member implements each side.

Cover:
1. C++ capture → local Python inference.
2. Backend → dashboard live events and history.
3. Dashboard → settings, consent, and device controls.
4. Backend → MongoDB.
5. Event export → Snowflake.
6. Alert generation → ElevenLabs → audio playback.

For audio, specify sample rate, channels, encoding, clip/window duration, framing, size limits, and who resamples. Distinguish capture, inference, and upload/event cadence.

For detections, define a canonical event schema including event/device IDs, time, label, model score, severity, and processing metadata. Do not treat a model score as a calibrated probability without justification.

Choose polling, SSE, or WebSocket for the MVP and justify one choice. Provide a full sample event moving through the system.
